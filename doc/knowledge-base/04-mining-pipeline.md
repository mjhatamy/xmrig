# 04 — Mining pipeline: job → dataset → workers → hash loop → share

## 1. `Miner::setJob(job, donate)` — `src/core/Miner.cpp`

1. `backend->prepare(job)` (CPU: selects the Argon2 impl used for the RandomX cache).
2. If the algorithm changed (e.g. `rx/0` → `rx/2` at the FCMP++ fork): `stop()` all
   workers and `RxAlgo::apply(algo)` — copies the variant's parameters into the global
   `RandomX_CurrentConfig` and re-runs `RandomX_ConfigurationBase::Apply()`
   (`src/crypto/randomx/randomx.cpp`), which rebuilds the 256-entry opcode→JIT-handler
   table from the instruction frequencies.
3. Nonce reset policy: reset unless switching back from donation with the same user
   job, or the pool resent the same blob with a new difficulty (`isEqualBlob`); always
   reset when the RandomX dataset changes.
4. `Rx::init(job, rxConfig, cpuConfig)` (`src/crypto/rx/Rx.cpp`): first-time setup
   (scratchpad prefetch mode, huge-pages-JIT flag, AVX2 dataset init, soft-AES impl,
   SSE4.1/AVX2 Blake2b on x86), MSR mod on x86 Linux/Windows, then
   `RxQueue::enqueue(seed, …)` if the dataset for this seed isn't ready. Returns `ready`.
5. If ready: `handleJobChange()` → `Nonce::reset` (if needed) →
   `backend->setJob(job)` → `Nonce::touch()` (bump sequence ⇒ workers pick it up) →
   `Nonce::pause(false)`. If not ready, workers stay paused until
   `Miner::onDatasetReady()` fires on the loop thread.

## 2. Dataset build — `RxQueue` → `RxBasicStorage` → `RxDataset`

Background thread `RxQueue::backgroundInit` (one per process):

1. Allocate (once): dataset `VirtualMemory(2080 MiB)` with huge/1 GB pages if possible
   (`RxDataset::allocate`), cache 256 MiB (`RxCache`). With hwloc + NUMA, one dataset copy
   per NUMA node (`RxNUMAStorage`). Log: `allocated 2336 MB (2080+256) huge pages 100% …`.
2. `RxCache::init(seed)` → `randomx_init_cache` → **Argon2d** (256 MiB, 3 passes, salt
   `"RandomX\x03"`) + generate 8 SuperscalarHash programs from Blake2b(seed); on x86 and
   ARM64 those 8 programs are JIT-compiled into one dataset-item function
   (`initCacheCompile` → `generateSuperscalarHash`).
3. `RxDataset::init` splits the 34,078,719 dataset items (64 B each) over `init` threads
   (default: all logical CPUs, `RxConfig::threads`) (`randomx_init_dataset`). Each item = 8 rounds of {superscalar program on 8 registers,
   XOR a pseudo-random 64-byte cache line}. Measured here: **5.6 s with 4 threads**.
4. `onReady` → `uv_async` → `Miner::onDatasetReady` → workers resume.

`--randomx-mode=light` skips the dataset (256 MiB only) and computes dataset items on the
fly inside the VM loop (`vm_compiled_light`): measured **213 H/s vs ~1950 H/s** in fast mode
on the same 4 vCPUs (~9× slower; 18.7 ms vs 2.08 ms per hash). Only the cache is built
(0.25 s here).

## 3. Threads — `CpuBackend::setJob` → `Workers::start`

`CpuConfig::get(miner, algo)` returns the thread list for the `rx` profile; if absent it
is generated by `CpuConfig_gen.h` → `Cpu::info()->threads(algo, limit)`:

| CPU info backend | Rule for RandomX |
|---|---|
| `HwlocCpuInfo` on x86 | per L3 (or L2) cache: `threads ≈ (L3 + extra L2) / 2 MiB`, capped by cores; vendor-specific tweaks (Zen4/5 extra L2, Intel P/E with exclusive L3) |
| `HwlocCpuInfo` on ARM/RISC-V | `allThreads()` — **one thread per PU, affinity = PU index, cache sizes and `max-threads-hint` ignored** |
| `BasicCpuInfo` (no hwloc) on ARM | `CpuThreads(hardware_concurrency())` — one per core, no affinity |

Each thread entry becomes a `Thread<CpuLaunchData>`; `Thread::start` uses `std::thread`,
except on Apple where it uses pthreads and, when an affinity is set, applies a Mach
`THREAD_AFFINITY_POLICY` tag (a hint the macOS arm64 scheduler does not honour).
`Workers::onReady` creates the `CpuWorker<1>` (RandomX intensity is always 1), runs
`selfTest()`, and reports `READY threads N/N`.

Per worker allocation (`CpuWorker` ctor): a 2 MiB scratchpad `VirtualMemory`
(huge page if possible); the VM itself is created lazily in `allocateRandomX_VM` →
`RxVm::create` → `randomx_create_vm(flags)` with
`RANDOMX_FLAG_FULL_MEM | RANDOMX_FLAG_JIT | RANDOMX_FLAG_HARD_AES` on any modern CPU
(the VM objects are carved from a 2 MiB per-NUMA-node pool).

## 4. The hash loop — `CpuWorker<N>::start()` (`src/backend/cpu/CpuWorker.cpp`)

```text
while (sequence > 0):                       # 0 = stop
  wait while Nonce::isPaused()               # dataset rebuild, no pool, user pause
  consumeJob()                               # copy job blob, reserve first nonce block
  first = true
  while (!Nonce::isOutdated(CPU, m_job.sequence())):
      nonce_prev = current nonce             # the hash produced below belongs to it
      if first: randomx_calculate_hash_first(vm, tempHash, blob)   # Blake2b(blob) + fill scratchpad
      nextRound()                            # nonce++, every 32768 hashes Nonce::next() atomically
      randomx_calculate_hash_next(vm, tempHash, blob_with_new_nonce, out=m_hash)
          # = 8 x { generate program (AES) ; JIT compile ; execute 2048 iterations ; Blake2b(regs) }
          #   then: Blake2b(new blob) and hashAndFill: AES-hash the scratchpad (result of
          #   the OLD nonce) while AES-filling it for the NEW nonce, in one pass.
      if rx/2: m_hash = Blake2b(prev_blob || m_hash)   # commitment; raw hash kept as m_commitment
      if *(uint64*)(m_hash+24) < job.target: JobResults::submit(job, nonce_prev, m_hash, commitment)
      m_count++
      if yield: std::this_thread::yield()
```

Notes:

* **Software pipelining**: xmrig fuses the final `hashAes1Rx4` of hash *n* with the
  `fillAes1Rx4` of hash *n+1* (`hashAndFillAes1Rx4`, `aes_hash.cpp`), so the 2 MiB
  scratchpad is streamed once per hash instead of twice.
* **Nonces**: global atomic counter per job index (user/donate), each thread reserves
  32768 at a time (`kReserveCount`) to avoid cache-line ping-pong; nicehash mode keeps
  the top 8 bits from the pool (`nonceMask = 0xFFFFFF`).
* **Share check**: only the top 64 bits of the 256-bit hash are compared to the 64-bit
  target; the pool re-verifies.
* **Job switch latency**: ≤ one hash (~2 ms here, ~2–5 ms on a laptop core).
* **Yield**: `sched_yield()` once per hash (~400–500/s per thread) — negligible cost,
  but `--cpu-no-yield` removes it.

## 5. Hashrate accounting

`Workers::tick` (every 500 ms on the loop) reads each worker's `m_count` into a
`Hashrate` ring buffer; reported windows are 10 s / 60 s / 15 min
(`Hashrate::ShortInterval/MediumInterval/LargeInterval`). `h` prints per-thread rates —
the fastest way to see P-core vs E-core differences on Apple Silicon.
